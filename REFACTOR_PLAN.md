# State Management Refactoring Plan

## Hard Battlefield Portal Constraints

This refactor is for Battlefield 6 Portal mode, not normal Node/browser TypeScript.

**Non-negotiables:**

1. **Single file only.** The final script must be self-contained in `conquest.ts`.
2. **Only event handlers are exported.** No exported classes, constants, helpers, registries, or state.
3. **No new `state.ts`.** All state types/helpers live as non-exported top-level declarations in `conquest.ts`.
4. **Avoid `modlib` long-term.** `modlib` is integrated into the runtime / present to make the current code compile, but it is buggy and should be phased out.
5. **If `modlib` is used, the required import format is exactly** `import * as modlib from 'modlib';`.
6. **Do not import `mod`.** Portal exposes `mod` globally; `mod` does not need and should not get an import.
7. **Confirmed supported TS/JS constructs:** `Map`, `Set`, classes, native arrays, native array `.push()`, and top-level `let` mutation are supported in this Portal runtime.
8. **Confirmed leave event semantics:** `OnPlayerLeaveGame(eventNumber: number)` receives the leaving player's object ID.

Validation command for exports after each phase:

```bash
grep -n "^export " conquest.ts
```

Expected result: only Portal event handlers such as `OngoingGlobal`, `OnGameModeStarted`, `OnPlayerJoinGame`, etc.

---

## Overview

Replace 555 `mod.GetVariable` / `mod.SetVariable` / `mod.ObjectVariable` calls in `conquest.ts` with typed in-file TypeScript state.

This is also the foundation for a longer-term migration toward cleaner game logic. The first priority is replacing Portal variable state safely; after that, rename autogenerated helper functions to sane domain names, then move event logic into non-exported classes/managers.

Primary state shape:

- `PlayerState` keyed by `mod.GetObjId(player)`
- `TeamState` keyed by `mod.GetObjId(team)`
- `CapturePointState` keyed by `mod.GetObjId(capturePoint)`
- plain top-level runtime variables for global mutable state
- direct constants for configuration flags/settings

**Why object IDs and not object handles?**

Each call to APIs such as `mod.GetTeam(1)` can return a fresh opaque handle. A `Map<mod.Team, TeamState>` or `Map<mod.Player, PlayerState>` can miss even when referring to the same underlying object. `mod.GetObjId()` is the stable identity.

**Files:**

| File | Action |
|---|---|
| `conquest.ts` | **MODIFIED** — all state, helpers, and event handlers remain here |
| `state.ts` | **DO NOT CREATE** |
| `modlib/index.ts` | **DEPRECATED DEPENDENCY** — keep only while current code needs it; replace usage over time |
| `tsconfig.json` | no required change |

## Phase 1: In-File State Foundation

Add this near the top of `conquest.ts`, after the existing `modlib` import while it still exists. Do not add any `mod` import. Long-term goal is to remove `modlib` usage; until then, keep the exact required import format.

Do **not** export any of this.

Phase 1 should be mostly additive. It should compile with the existing Portal variable code still present. Avoid migrating behavior in this phase except for adding safe helpers/state containers.

Phase 1 deliverables:

- top-level non-exported constants/classes/registries added to `conquest.ts`
- no new files
- no new exports
- no `mod` import
- `getPlayerState()` caches the latest player handle and updates `playerById`
- `getCapturePointState()` caches the latest capture point handle and updates `capturePointById`
- team state is initialized only for gameplay teams 1 and 2; neutral team is handled separately
- init helpers are idempotent and safe to call from every exported event handler

### 1g. Capture Point State

Preserve old-progress vs new-progress ordering. UI message logic depends on knowing whether progress increased or decreased.

```ts
class CapturePointState {
    id: number;
    progress = 0;
    uiSize: mod.Vector;
    uiPosition: mod.Vector;

    constructor(public capturePoint: mod.CapturePoint) {
        this.id = mod.GetObjId(capturePoint);
        this.uiSize = mod.CreateVector(0, 7, 0);
        this.uiPosition = mod.CreateVector(-110, 200, 0);
    }

    setProgressVisuals(progress: number): void {
        const width = mod.Floor(mod.Multiply(220, progress));
        this.uiSize = mod.CreateVector(width, 7, 0);
        this.uiPosition = mod.CreateVector(
            mod.Add(-110, mod.Floor(mod.Divide(width, 2))),
            200,
            0,
        );
    }
}
```

Usage pattern:

```ts
const cpState = getCapturePointState(cp);
const oldProgress = cpState.progress;
const newProgress = mod.GetCaptureProgress(cp);

if (oldProgress !== newProgress) {
    cpState.setProgressVisuals(newProgress);
    CapturePointUI_Manager(cp, oldProgress, eventInfo);
    cpState.progress = newProgress;
}
```

### 1h. Registries and Accessors

```ts
const playerStates = new Map<number, PlayerState>();
const teamStates = new Map<number, TeamState>();
const capturePointStates = new Map<number, CapturePointState>();

function getPlayerState(player: mod.Player): PlayerState {
    const id = mod.GetObjId(player);
    playerById.set(id, player);

    let state = playerStates.get(id);
    if (!state) {
        state = new PlayerState(player);
        playerStates.set(id, state);
    } else {
        // Handles can be fresh/opaque. Keep latest handle.
        state.player = player;
    }
    return state;
}

function tryGetTeamState(team: mod.Team): TeamState | null {
    ensureStateInitialized();
    return teamStates.get(mod.GetObjId(team)) ?? null;
}

function getTeamState(team: mod.Team): TeamState {
    const state = tryGetTeamState(team);
    if (state) return state;

    // Neutral/non-gameplay teams should not have TeamState. Fix call sites to use
    // isNeutralTeam()/sameTeam() checks instead of asking for score state.
    mod.SendErrorReport(mod.Message("Missing gameplay TeamState for team {}", mod.GetObjId(team)));
    return teamStates.get(mod.GetObjId(TEAM_1))!;
}

function getCapturePointState(cp: mod.CapturePoint): CapturePointState {
    const id = mod.GetObjId(cp);
    capturePointById.set(id, cp);

    let state = capturePointStates.get(id);
    if (!state) {
        state = new CapturePointState(cp);
        capturePointStates.set(id, state);
    } else {
        state.capturePoint = cp;
    }
    return state;
}

function sameTeam(a: mod.Team, b: mod.Team): boolean {
    return mod.GetObjId(a) === mod.GetObjId(b);
}

function isNeutralTeam(team: mod.Team): boolean {
    ensureStateInitialized();
    return sameTeam(team, TEAM_NEUTRAL);
}
```

Avoid `throw new Error(...)` in Portal gameplay code unless tested. Prefer diagnostics plus a safe fallback. Also avoid silently creating `TeamState` for neutral/non-gameplay teams because that can hide bad score logic.

### 1i. Cached Handles

Cache common handles, but initialize them inside event/init code.

```ts
let stateInitialized = false;
let stateInitializing = false;

let TEAM_NEUTRAL: mod.Team;
let TEAM_1: mod.Team;
let TEAM_2: mod.Team;

const teamById = new Map<number, mod.Team>();
const capturePointById = new Map<number, mod.CapturePoint>();
const playerById = new Map<number, mod.Player>();

function ensureStateInitialized(): void {
    if (stateInitialized || stateInitializing) return;
    stateInitializing = true;

    TEAM_NEUTRAL = mod.GetTeam(0);
    TEAM_1 = mod.GetTeam(1);
    TEAM_2 = mod.GetTeam(2);

    teamById.set(mod.GetObjId(TEAM_NEUTRAL), TEAM_NEUTRAL);
    teamById.set(mod.GetObjId(TEAM_1), TEAM_1);
    teamById.set(mod.GetObjId(TEAM_2), TEAM_2);

    const allCPs = mod.AllCapturePoints();
    for (let i = 0; i < mod.CountOf(allCPs); i++) {
        const cp = mod.ValueInArray(allCPs, i) as mod.CapturePoint;
        getCapturePointState(cp);
    }

    initRuntimeValues();
    initTeams();
    initStaticArrays();

    stateInitialized = true;
    stateInitializing = false;
}
```

Call `ensureStateInitialized()` at the start of every exported event handler, or at least every handler that may touch state. This avoids ordering bugs between `OngoingGlobal` and `OnGameModeStarted`.

Do not call `getTeamState()` from inside `initRuntimeValues()` or `initStaticArrays()` before `initTeams()` has run.

## Phase 2: Rename Autogenerated Internal Functions

Do this early, after the in-file state foundation is available but before deeper state migration. Cleaner names make the later player/team/global migrations much easier to review.

The current file contains many rule-generated function names such as:

- `OnPlayerDamaged_AI_Target_Shooter`
- `OnPlayerDamaged_AI_Target_Shooter_Condition`
- `OnPlayerDamaged_AI_Target_Shooter_Action`
- `OngoingCapturePoint_Capture_Times`
- `OngoingCapturePoint_Capture_Times_Action`
- `OnCapturePointCaptured_On_Capture`
- `OnPlayerJoinGame_Sets_Scoreboard`

These should be renamed to clearer non-autogenerated names.

Keep Portal event handler names unchanged. These must remain exported with their Portal-required names:

```ts
export function OnPlayerDamaged(...) { ... }
export function OngoingCapturePoint(...) { ... }
export function OnPlayerJoinGame(...) { ... }
```

Only rename internal helpers, conditions, and actions.

Recommended naming pattern:

| Current Pattern | New Pattern |
|---|---|
| `OnPlayerDamaged_AI_Target_Shooter` | `handleAIDamagedTargeting` |
| `OnPlayerDamaged_AI_Target_Shooter_Condition` | `shouldAITargetDamager` |
| `OnPlayerDamaged_AI_Target_Shooter_Action` | `targetAIDamager` |
| `OngoingCapturePoint_Capture_Times` | `updateCapturePointProgressRule` or remove wrapper entirely |
| `OngoingCapturePoint_Capture_Times_Action` | `runCapturePointProgressLoop` |
| `OnCapturePointCaptured_On_Capture_Action` | `handleCapturePointCaptured` |
| `OnPlayerJoinGame_Sets_Scoreboard_Action` | `handlePlayerJoined` |
| `OngoingGlobal_Update_Score_and_Time_Action` | `updateScoreTimeAndAI` |

Prefer domain/action names over event-source names. For example:

```ts
function shouldAITargetDamager(eventInfo: PlayerDamageEvent): boolean { ... }
async function targetAIDamager(eventInfo: PlayerDamageEvent): Promise<void> { ... }
function handleAIDamagedTargeting(conditionState: ConditionState, eventInfo: PlayerDamageEvent): void { ... }
```

During transition, it is acceptable to keep wrapper functions if condition-state logic still needs them. Long-term, wrappers should disappear as event handlers dispatch into controllers.

Rename strategy:

1. Rename one event group at a time.
2. Rename `_Condition` first, then `_Action`, then wrapper.
3. Update the exported event handler call sites immediately.
4. Run TypeScript after each group.
5. Do not change behavior while renaming.

Suggested order:

1. player join/deploy/leave helpers
2. scoreboard/UI helpers
3. capture point helpers
4. AI targeting/deploy helpers
5. win-condition/game-loop helpers
6. OOB/team-switch helpers

Do not rename exported Portal event handlers.

## Phase 3: Remove `modlib` Dependency Where Practical

`modlib` should be treated as a temporary compatibility layer only. Replace it with small local helpers or direct code.

### 3a. Replace Boolean Helpers

Current:

```ts
modlib.And(a, b, c)
```

Preferred:

```ts
a && b && c
```

or use Portal `mod.And(...)` only when required by API semantics.

### 3b. Replace `modlib.ConvertArray`

Local helper:

```ts
function modArrayToNative<T>(array: mod.Array): T[] {
    const result: T[] = [];
    const count = mod.CountOf(array);
    for (let i = 0; i < count; i++) {
        result.push(mod.ValueInArray(array, i) as T);
    }
    return result;
}
```

### 3c. Replace `modlib.FilteredArray`

If the result will be consumed by native TS:

```ts
function filterModArrayToNative<T>(array: mod.Array, predicate: (value: T) => boolean): T[] {
    const result: T[] = [];
    const count = mod.CountOf(array);
    for (let i = 0; i < count; i++) {
        const value = mod.ValueInArray(array, i) as T;
        if (predicate(value)) result.push(value);
    }
    return result;
}
```

If the result must be passed to Portal array APIs:

```ts
function filterModArray(array: mod.Array, predicate: (value: any) => boolean): mod.Array {
    let result = mod.EmptyArray();
    const count = mod.CountOf(array);
    for (let i = 0; i < count; i++) {
        const value = mod.ValueInArray(array, i);
        if (predicate(value)) result = mod.AppendToArray(result, value);
    }
    return result;
}
```

### 3d. Replace `modlib.IsTrueForAny` / `IndexOfFirstTrue`

Use native loops when possible. Avoid generic helpers around Portal arrays unless needed.

### 3e. Replace `modlib` Condition State

Current event exports use `modlib.getGlobalCondition`, `modlib.getPlayerCondition`, etc. Long-term, move a minimal local condition-state implementation into `conquest.ts` and call that instead.

This removes the need for the `modlib` import while preserving current event gating behavior. Until all `modlib` usage is removed, keep the exact required import: `import * as modlib from 'modlib';`.

```ts
class ConditionState {
    lastState = false;

    update(newState: boolean): boolean {
        if (!newState) {
            this.lastState = false;
            return false;
        }
        if (this.lastState) return false;
        this.lastState = true;
        return true;
    }
}
```

Then implement local `getGlobalCondition`, `getPlayerCondition`, and `getCapturePointCondition` keyed by object ID.

**Deliverable:** most or all `modlib.` references removed. Eventually remove:

```ts
import * as modlib from 'modlib';
```

## Phase 4: Eliminate Scoping Anti-Patterns

Replace blocky-runtime workarounds with native local variables.

### 4a. Iterator Globals → Local `let`

Replace:

```ts
for (let iteratorVar = 0; iteratorVar < mod.CountOf(array); iteratorVar += 1) {
    mod.SetVariable(iteratorGlobalVar, iteratorVar);
    doSomething(mod.ValueInArray(array, mod.GetVariable(iteratorGlobalVar)));
}
```

with:

```ts
for (let i = 0; i < mod.CountOf(array); i++) {
    doSomething(mod.ValueInArray(array, i));
}
```

Include the player object iterator too:

```ts
mod.ObjectVariable(eventInfo.eventPlayer, iteratorPlayerVar)
```

This appears in `FX_Reset` and should become a local `let`.

### 4b. `AppendGlobalVar` / `AppendToArray` → Native Arrays

Use native arrays for:

- UI ID pool
- objective tracking widget names
- flag letters
- bot names
- flag announce enum list

Example:

```ts
function initFlagLetters(): void {
    flagLetters.length = 0;
    flagLetters.push("A", "B", "C", "D", "E", "F", "G");
}
```

### 4c. `tempGlobalVar` → Local Variables

Replace scratch global array writes with local variables.

Example:

```ts
const validPlayers = filterModArray(
    mod.GetPlayersOnPoint(eventInfo.eventCapturePoint),
```

```ts
const validPlayers = filterModArrayToNative<mod.Player>(
```

Then use `.length` and normal indexing.

### Player Cleanup

Portal's generated signature is:

```ts
OnPlayerLeaveGame(eventNumber: number): void;
```

`eventNumber` is confirmed to be the leaving player's object ID, so cleanup can be deterministic by ID.

```ts
function removePlayerStateById(playerId: number): void {
    const state = playerStates.get(playerId);
    if (state) {
        releasePlayerUiId(state);
        playerStates.delete(playerId);
    }
    playerById.delete(playerId);
}

export function OnPlayerLeaveGame(eventNumber: number): void {
    ensureStateInitialized();
    removePlayerStateById(eventNumber);
}
```

Keep the current pool-rebuild fallback in `PlayerUISetup` during transition, but it should become a safety net rather than the primary cleanup mechanism.

### 7g. Remove UI ID Pool

Do not keep the numeric text-object pool long term. The current pool exists only to generate unique per-player root UI widget names. The old block-editor-generated list had quirks around censored block text, but TypeScript does not need to preserve those exact skipped values as long as the pool has enough unique names during transition.

Replace the pool with deterministic names based on the player's object ID:

```ts
function playerRootWidgetName(player: mod.Player): string {
    return `PlayerRoot_${mod.GetObjId(player)}`;
}

function playerRootWidgetNameFromId(playerId: number): string {
    return `PlayerRoot_${playerId}`;
}
```

Then player setup becomes:

```ts
const state = getPlayerState(eventInfo.eventPlayer);
state.uniqueUiId = playerRootWidgetName(eventInfo.eventPlayer);

mod.DeleteUIWidget(mod.FindUIWidgetWithName(state.uniqueUiId)); // defensive cleanup if it exists
mod.AddUIContainer(
    state.uniqueUiId,
    mod.CreateVector(0, 0, 0),
    mod.CreateVector(10000, 10000, 0),
    mod.UIAnchor.TopCenter,
    eventInfo.eventPlayer,
);
```

On leave, delete by deterministic name when possible:

```ts
function removePlayerStateById(playerId: number): void {
    const state = playerStates.get(playerId);
    const rootName = state?.uniqueUiId || playerRootWidgetNameFromId(playerId);
    mod.DeleteUIWidget(mod.FindUIWidgetWithName(rootName));
    playerStates.delete(playerId);
    playerById.delete(playerId);

```

This eliminates:

- `ID_PoolGlobalVar`
- `UniqueUI_ID_UsedGlobalVar`
- `uiIdPool`
- `activeUiIds`
- pool rebuild logic
- the numeric-name pool entirely

During transition, a simple `"1"` through `"105"` pool is acceptable if it has the correct number of unique elements. Long term, replace it with `PlayerRoot_<objectId>` and delete the pool.

## Phase 18: Rule Trigger Simplification

The `*Rule` wrappers still expose the old generated-rule shape. They now hide condition-slot lookup internally, but many wrappers still perform edge detection on conditions that are always `true`:

```ts
function initGameSettingsRule() {
    const condition = getGlobalCondition(GlobalConditionSlot.InitGameSettings);
    const state = true;
    if (condition.update(state)) {
        conquestGame.initGameSettings();
    }
}
```

This is not a meaningful gameplay condition. It is an initialization/lifecycle action that should be expressed directly.

### Phase 18a: Remove always-true wrappers where the event is already one-shot

Start with wrappers whose `newState` is always `true` and whose exported event is naturally one-shot or discrete.

Candidate wrappers:

```ts
initGameSettingsRule()
setupMapRule()
processReviveRule(eventInfo)
handlePlayerDeathRule(eventInfo)
addEquipmentRule(eventInfo)
handlePlayerJoinRule(eventInfo)
handleCapturePointCapturedRule(eventInfo)
handleTeamSwitchAndRepelRule(eventInfo)
runCaptureProgressRule(eventInfo)
```

Migration strategy:

1. Move any deliberate waits into the controller method if they belong to the behavior.
   - Example: the `await mod.Wait(0.2)` before capture handling should become part of `CapturePointController.onCaptured(...)` if the wrapper is removed.
2. Replace event-handler calls with direct controller calls.
   - `initGameSettingsRule()` becomes `conquestGame.initGameSettings()` in `OngoingGlobal()` or, preferably, an explicit startup helper.
   - `setupMapRule()` becomes `conquestGame.setupMap()` in `OnGameModeStarted()`.
3. Delete the wrapper after the direct call compiles.
4. Run TypeScript after each small group.

Important: Do not blindly remove all always-true wrappers at once. Some event handlers may fire repeatedly in Portal, and the old rising-edge `ConditionState` may have been suppressing duplicate async loops. For each wrapper, verify whether the exported Portal event is one-shot, discrete, or ongoing.

### Phase 18b: Introduce explicit startup/lifecycle state

`initGameSettingsRule()` is really a startup initialization guard, not a rule. Replace it with explicit lifecycle state.

Recommended shape:

```ts
let gameSettingsInitialized = false;

function ensureGameSettingsInitialized(): void {
    if (gameSettingsInitialized) return;
    conquestGame.initGameSettings();
    gameSettingsInitialized = true;
}
```

Then `OngoingGlobal()` can call:

```ts
ensureGameSettingsInitialized();
```

This says what the code means without consuming a rule condition slot.

Be careful with match restarts. If Portal reuses script state across rounds, reset this flag at the correct lifecycle boundary before starting a new match.

### Phase 18c: Keep edge-detection only where it is semantically needed

Wrappers with real changing conditions may still need rising-edge behavior:

```ts
updateScoreTimeRule()
trackScoreRule()
playNearEndMusicRule()
endGameRule()
notifyCaptureRule(eventInfo)
showCaptureUIRule(eventInfo)
hideCaptureUIRule(eventInfo)
aiTargetDamagerRule(eventInfo)
```

For these, either keep the wrapper or replace it with a clearer helper such as:

```ts
function runRisingEdgeRule(
    edge: ConditionState,
    state: () => boolean,
    action: () => void | Promise<void>,
): void {
    if (edge.update(state())) {
        action();
    }
}
```

Do not remove edge detection from ongoing/tick rules unless the action is idempotent or intentionally should run every tick.

### Phase 18d: Rename the abstraction if it remains

If `ConditionState` remains after cleanup, rename it to clarify behavior:

- `ConditionState` → `RisingEdgeState`
- `Conditions` → `RisingEdgeStore`
- `getPlayerCondition(...)` → `getPlayerRisingEdge(...)`

This makes it clear that the state is not a generic condition; it is a false→true trigger.

Deliverable:

- startup actions use explicit lifecycle guards, not always-true rule wrappers
- one-shot/discrete event actions call controllers directly where safe
- rising-edge state remains only for rules that actually need false→true edge detection
- exported event handlers remain the only exports
- TypeScript compiles after each small cleanup pass
